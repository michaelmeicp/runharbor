# Discovery plan

The goal is to earn attention through a useful, credible workflow. Star growth is an outcome to observe, not a promise or a reason to inflate functionality.

## Before a public preview

- Confirm permission to publish the narrower mock-only development preview despite the original first-release gate.
- Keep the status limitation visible before installation instructions.
- Use real screenshots and a reproducible zero-key demo.
- Verify clean installs and CI. Enable private vulnerability reporting and appropriate repository protections where the account plan allows.
- Configure a real private security/conduct contact. Do not invent an email address or support commitment.

## Repository positioning

Description: **Scheduled agents, organized results, and an inbox for what needs you. Local-first workbench; mock-only development preview.**

Candidate topics: `ai-agents`, `agent-orchestration`, `local-first`, `scheduler`, `automation`, `sqlite`, `developer-tools`.

The first screen should explain the inbox/results distinction. A reader should discover in under a minute both the benefit and the current limitation. No vendor logos, unsupported compatibility badges, fabricated adoption numbers, or copied competitor star counts.

## Launch assets prepared

- English README and Traditional Chinese companion.
- Actual screenshots of inbox, outputs, schedules, usage, and mobile layout.
- Bug and workflow-request templates, contribution guidance, and a transparent requirement matrix.
- Mock-only two-minute walkthrough.

## Suggested launch copy — draft only

> I’m building RunHarbor: a local workbench where scheduled agents leave organized results instead of a growing list of chats. The inbox is for questions and exceptions. This first development preview is mock-only, so you can try the workflow without an API key or model spend. I’m looking for feedback on the workflow and help verifying the live-adapter security boundaries.

This copy has **not** been posted to social networks, communities, or other people's repositories. Public communication needs a separate instruction.

## Measure after launch

Record a dated baseline for stars, unique visitors, clones, issues, and successful first-run reports. Check weekly, where GitHub exposes the data. Prioritize install failures and workflow confusion before adding promotion. Avoid bought stars, engagement exchanges, unsolicited bulk outreach, and unsupported comparison claims.

The strongest next release milestone is a securely verified live task loop, not more promotional badges.
